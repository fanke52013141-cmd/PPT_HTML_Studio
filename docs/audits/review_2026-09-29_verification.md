### PPTX 重试额外缺口

`pptx_service.py:234–239` 的首次提交传 account_id、input_digest、impact_snapshot；`:344` 的重试没有传。`:528–530` 与 `:564` 的校验均以 queued_digest 非空为前提。

因此只修账号参数仍不够：重试任务没有首发任务的输入变化保护。本次未完整运行后台导出，这一结论来自明确的参数与条件分支。应给两种创建方式使用相同的准备函数，并为旧任务兼容定义显式规则，避免用空字符串表示“跳过保护”。

## 推荐实施顺序

### 第一批：恢复勾画基本功能并防止保存污染

范围：R4-001/002/003/005/006。移动方法、补加载、分离网络与渲染错误、按页保存草稿与请求代次、冲突恢复。

关键验收：

- 所有新增路由使用实际服务装配测试，不能 mock 掉缺失方法。
- 服务端已提交后覆盖层故障，不会重新发送 add。
- A 项目的成功/失败/轮询回调晚于 B 项目载入，不改变 B 的任何状态。
- 409、422 保留可恢复草稿，不能无限自动重试或静默丢操作。
- add 对“服务端已执行、客户端未收到响应”的重试幂等。

### 第二批：确认、新鲜度与导出一致性

范围：R4-004、R2-001、R1-002、R4-007，补 Step 2 CAS。

- 已确认标注修改颜色/几何/时间后，旧 timeline 不得通过；重新确认导出应使用新结果。
- PPTX 首发与重试都固化账号和当前输入指纹，输入变化统一拒绝旧结果。
- 重复/空 ID 返回校验错误且无任何落盘副作用；空页列表仍可保存。
- 分镜并发冲突返回可恢复的 409，不允许后到的旧快照覆盖新版本。

### 第三批：账号闭环、ZIP 与历史数据

范围：helper、annotation detect/plan 线程、ZIP 限制、0014 修复方案。

- HTTP 请求和后台任务都以已验证项目账号为准；切账号、重启、重试仍保持归属。
- 双账号 CRUD、下载、删除、任务提交都验证隔离。
- ZIP 主条目和资源的每项/总量/条目数有界，验证失败零写入。
- 旧数据库副本演练迁移，不能修改 0014 文件或覆盖用户明确的模式选择。

### 第四批：检查门与剩余可靠性

Ruff 清理贯穿前三批；最后全量检查、原子写收敛、低 RPM/异常重试、调速并发，再做浏览器与视频人工验收。

每批提交单独的问题修复和行为回归。不要把全部问题混在一次格式化、重构和功能修复中；不要以已有 65 项通过代替新缺口测试。

最终最低验证：隔离环境运行 `python scripts/run_checks.py --level full --with-remotion`，解释所有 skip/xfail；真实浏览器完成识别/规划/编辑/保存/冲突/切页；横竖屏各检查一份含勾画输出，并做一次非 default 账号 PPTX 失败重试。
