# 依据规则生产与兼容演进

所属契约包：0.5.0。本文件规定未来 HTML 路线的生产和规则维护方式。
当前只有设计规则；下述运行校验、记录与迁移须随对应能力实现，不视为已上线。

## 1. HPS-014：每次生产携带规则与输入版本

### 1.1 生产前提

执行某种能力前，必须有其定义卡、输入模型、实现与支持范围。仅存在候选名称不代表
可以生成这种组件。AI、人工编辑和批量生成使用同一套数据接口与校验；不得对 AI
产物放宽门禁，也不能仅依赖模型记住文档。

每次生产明确：材料与来源、必讲内容、受众与目的、输出比例/格式、内容修订、规则
包版本、风格/组件/布局/动作版本、允许的降级及人工保护。缺少关键参数时可以
先产出标记明确的草稿，不能把待确定项自动当成已经验收。

### 1.2 生产阶段与交付

| 阶段 | 使用哪些规则 | 产出 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 1 内容规划 | 内容关系、覆盖与文档层级 | 页面意图、讲稿、内容映射 | 必讲项有归属，来源与关系无未处理矛盾 |
| 2 结构组装 | 公共组件、布局、配方与目标 | 结构化页面实例 | 类型、版本、字段、引用和公共目标可解析 |
| 3 风格解析 | 参数归属、覆盖、支持矩阵 | 解析样式与兼容诊断 | 无未处理缺项或约束冲突 |
| 4 素材准备 | 槽位、资源、锚点与画风 | 已选择/生成的具体资源版本 | 正式输出所用资源可用且适配；草稿明确占位 |
| 5 排版定位 | 字体、测量、容量、坐标链 | 几何、分行、目标映射 | 无阻断溢出/错位/遮挡，字体采用可追溯方案 |
| 6 动作编译 | 语块映射、状态、通道和时间 | 确定时间表 | 无悬空目标、冲突或不明时长 |
| 7 预览审阅 | 就绪与视觉参考集 | 各阶段画面、诊断、审阅记录 | 机器检查与对应视觉检查完成 |
| 8 作品输出 | 能力报告、固定输入、输出策略 | HTML/图片/视频/PPTX 与来源记录 | 不静默降级，结果对应同一输入修订 |

运行实现可以合并执行步骤，但不能丢失这些输入、结果与检查。定义阶段只验收定义
材料；单页样板可使用固定文字、本地素材与手工时间，仍验证相同的目标和时间规则。

### 1.3 生产记录

未来每次正式输出记录作品/任务 ID、输入修订、契约包版本、实际选用的定义版本、
资源与字体哈希、渲染环境、布局/时间结果、输出配置、诊断、已采用的降级与产物。
所记录的是实际使用值，不能只有当时系统默认值。正在导出的快照不随编辑改变。

## 2. 问题定位与处理顺序

发现问题先保存最小复现材料：内容、版本、素材引用、目标时刻、期望/实际画面或数据。
优先复用原任务快照；不要求每次从整份课程重做。

| 判断 | 处理 |
| --- | --- |
| 实现没有遵守已有规则 | 修实现，原规则保留；增加能复现问题的验证 |
| 单个作品内容/参数无效 | 修实例或给出可操作诊断，不扩大公共容错 |
| 素材不适配或锚点过期 | 修资源要求/替换版本/重新锚定，并保留旧引用 |
| 风格参数或组合不成熟 | 修改该风格版本与参考集，复查它支持的样例 |
| 公共规则缺少场景 | 扩展规则、定义卡与实现，并分析既有实例 |
| 两条规则相互冲突 | 定位各自所有权，在同次修改中统一，记录取舍 |

诊断须指向对象、字段、规则编号及修复方向。不能把所有错误归结为“模型不稳定”。
缺少功能时先报告能力缺口，不能生成未经登记的 HTML 片段绕过模型和验收。

## 3. HPS-015：规则变更流程与版本

### 3.1 变更流程

1. 建立问题记录，关联规则 ID、复现材料、实际/期望结果和影响范围。
2. 按上一节判断应修规则、实现、风格、资源还是实例；明确规则真正的所有者。
3. 写出变更前后行为、旧数据及旧视觉是否受影响、哪些产物失效、怎样兼容和恢复。
4. 在同一变更中更新受影响的规范正文、索引版本、定义卡、字段模型/注册表和对应实现。未实现
   的部分保持明确状态，不能更新文档后声称运行能力已修好。仅修实现且规范未改变时，
   不必改写规则或提升契约包版本，记录实现修订及验证即可。
5. 验证原问题、新行为与受影响的旧样例；记录采用的新版本和仍未覆盖的范围。
6. 在 CHANGELOG 中登记变更，并说明已有作品继续使用旧版本还是可显式升级。

常规兼容修复在既有任务授权范围内执行，不为每条规则增加用户审批。涉及无法从
上下文判断的业务或审美取舍时，再请用户选择；不能以兼容为理由静默改掉用户内容。

### 3.2 不同版本分别管理

| 版本/标识 | 管什么 | 何时改变 |
| --- | --- | --- |
| 契约包版本 | 本目录的整体规则基线 | 规范性内容改变；在 CHANGELOG 说明 |
| Schema 版本 | 数据字段、结构和解释 | 数据格式或语义改变 |
| 定义版本 | 组件、布局、风格、配方、动作的具体定义 | 对应定义/默认值/行为改变 |
| 内容 revision | 用户文档/页面源数据 | 实际内容或作者选择变化 |
| 资源版本/哈希 | 字体、图片、图标等实际文件 | 字节内容或锚点约定改变 |
| 实现/渲染环境版本 | 算法、浏览器、字体处理等 | 实际运行条件改变 |
| 输入摘要 | 某个派生产物的实际依赖 | 被依赖输入改变 |

本项目采用主、次、修订版本表达契约变化。修订版用于不改规范含义的勘误；次版本
用于保留旧行为的增量；破坏字段、目标含义、旧能力或默认语义的变更须声明为破坏性
并提升主版本。0.x 阶段也不能把破坏性变化伪装成兼容修复。

风格美化或算法修复可能保持数据兼容却改变像素，必须另列视觉影响；兼容不能只看
JSON 还能不能读。任何实际改变的资产、定义或实现都要可追溯，不能用旧版本号覆盖。
尚处设计基线阶段的规则修改可直接更新设计材料，但仍记录受影响定义和待实现状态。

## 4. HPS-016：旧作品兼容与升级

### 4.1 四种兼容性分别判断

| 兼容维度 | 判断问题 |
| --- | --- |
| 数据兼容 | 旧文档能否读取、写回而不丢字段或改变内容 |
| 语义/行为兼容 | 公开目标、组件职责、动作结果是否保持相同含义 |
| 视觉兼容 | 字体、布局、素材和分步画面是否变化，是否需要重新审阅 |
| 输出兼容 | 旧的可编辑/动画/媒体要求是否仍满足，是否新增降级 |

新增可选字段仍需验证其缺省值保留旧行为。字段改名、删除目标、改变字符索引单位、
改变动作结束策略、收紧允许范围等都可能破坏兼容，不能只因字段数量没变就忽略。

### 4.2 版本固定与迁移

已保存作品引用具体定义和资源版本；新建作品可以使用新默认，但不自动改旧作品。
旧文件通过已登记的版本读取器/迁移器处理，未知版本显式报告不支持，不猜测或丢字段。
旧解释器或资源不可用时，应说明无法按原条件重新渲染，而不是声称已经精确复现。

迁移先产生新修订，保留原修订及资源关系，提供字段、公开目标、外观和输出差异。
明确是否能逆向恢复；不可逆转换要保留源修订，而非编造逆变换。人工锁定不因升级
自动取消。迁移重复执行不得重复插入节点或制造多份相同修订，完成后重新校验引用、
排版、时间和输出要求。

不能迁移的项可以保持旧版、选择明确的兼容变体或请求具体内容处理。临时兼容层
登记用途、适用版本、限制、替代方式和后续移除条件，不无期限散落在组件代码中。

### 4.3 最新代码与固定作品规则

桌面快捷方式始终启动 D 盘唯一开发目录的当前代码，这条规范继续有效。当前代码
可以理解多个数据/定义版本，版本信息不意味着另起一份桌面运行副本。
作品版本固定是为了保存创作意图；最新程序应明确支持范围。历史导出可以直接保留
查看，要求按原条件重渲染时还需具备原资源与相应渲染能力，不能只靠一个版本号保证。

### 4.4 例子

例 A：某风格标题过大。修该风格参数并发布新版本；旧作品继续引用原版，升级后
重新排版和审阅。只改字号通常可复用讲稿音频，但会更新文字锚点和画面。

例 B：旧组件支持单行标题，现在希望两行。保留旧默认，新增已定义的可选能力或
通用变体；若直接把所有旧标题改成自动两行，就必须报告默认行为与视觉变化。

例 C：旧目标叫 description，新版本希望叫 body。优先维持旧公开目标或提供显式
别名/迁移；新场景统一写新名称。不得只改 DOM 后让旧动画找不到目标。

例 D：增加公式组件。新增公共能力和输出支持声明，各风格再登记覆盖；已有风格
缺少公式外观时给出明确兼容结果，不临时生成任意 HTML 或伪报可编辑 PPTX。

## 5. HPS-017：规则与验证同步

每条运行规则应逐步建立链路：规则 ID → 定义卡/Schema 字段 → 注册能力与实现 →
正常/边界/失败样例 → 校验或视觉验证 → 结果状态。当前索引标记为设计审查执行，
不表示存在机器校验器。只有对应代码和验证确实存在，才能更新其实施状态。

结构规则由 Schema/类型检查，目标和时间等跨对象规则由语义检查，几何由实际排版
检查，美感由参考样例与视觉审阅，导出兼容由目标格式实测。一个 JSON 校验器不能
代替全部检查，Prompt 也不是规则执行引擎。

新增或修复能力只验证相关范围，同时覆盖被影响的旧样例。不能为尚未实现的能力
写空洞测试，也不能为了某个失败样例删除约束。规则变更可能影响已有验收阈值时，
说明更新依据，不把新输出直接无条件覆盖成“正确参考图”。

## 6. 变更记录模板

每次规则变更至少记录以下字段，可先使用 Markdown，后续接入现有项目管理能力。

```text
问题/变更 ID：
关联规则 ID 与原版本：
复现输入或材料位置：
期望行为 / 实际行为：
根因归属：规则 / 实现 / 风格 / 资源 / 实例
修改内容及理由：
新契约包、定义、Schema 或实现版本：
数据 / 行为 / 视觉 / 输出兼容影响：
旧作品策略、迁移方式和恢复方式：
受影响的缓存、音频、定位、输出：
更新的定义卡、Schema、代码、样例：
已完成的验证及证据：
尚未完成或不支持的部分：
```
