# 通知精简记录（2026-09-29）

用户反馈：泛泛的“待核对”记录会不断累积，遮挡作品输出；重复的常驻通知也无法帮助完成操作。

## 本次处理

| 入口 | 调整 |
| --- | --- |
| 作品输出 | 移除项目影响清单、“前往检查”和“标记已查看”；生成按钮与作品列表回到页面主体。 |
| 图片替换、上传、重排 | 移除逐项列出旧文件和缓存的影响弹窗；默认归档可恢复的旧素材，并继续校验图片版本。显式删除图片仍确认删除范围。 |
| AI Mask | 不显示非阻断的“建议检查”通知和语块徽标；真正阻断结果的问题仍在 Mask 步骤就地显示。 |
| 自动保存 | 不再弹出分镜、旁白修改后的笼统核对提示；保存失败和并发冲突仍提示。 |
| 图片生成与一键生成 | 移除重复的常驻失败红点；图片失败页可直接重试，短暂错误提示列出失败页，一键进度面板显示阶段错误。 |
| 项目库 | 后台的 `waiting_for_review` 状态显示为“已暂停”，避免把普通用户引向无操作价值的审查任务。 |
| 全局提示 | 仅操作失败或校验阻断时弹出；成功、进度和普通警告静默。同一错误 60 秒内不重复弹出，屏幕上最多一条。 |

## 保留原则

- 输入缺失、保存冲突、任务失败等需要立即处理的问题，显示在对应操作附近或以短暂提示呈现。
- 用户明确执行删除等会移除当前内容的操作时，确认影响范围。
- `planning/pending_impacts.json` 和产物哈希校验继续供后台判断新旧素材；隐藏通知不代表将旧产物认定为当前版本。

此前通知频繁有两个直接原因：全局 `showToast` 仍允许 warning，且同一提示只在显示期间去重；后台任务每 1.2–3 秒轮询一次，HTTP 失败时通用 API 层自动弹窗，部分调用方还会再弹一次。现在只有失败或操作被输入校验阻断才进入通知容器，同一错误 60 秒内不重弹。视频、PPTX、音频、一键生成、项目库和数字人任务的状态轮询使用静默请求；任务失败继续显示在对应步骤，必要时给出一次失败提示。

## 第三轮：只保留失败/报错（2026-09-29 晚）

用户反馈：上一轮之后仍有大量"无关紧要"的通知弹出，感觉像是在不断触发 bug，
希望通知只服务于故障排查——出现即意味着真的失败了。

### 审查结论

全量核对 `showToast` 的 253 处调用（29 个前端模块）后确认：成功、进度和普通
警告已被上一轮静默，剩余的频繁弹窗全部来自一类误判——**输入引导与校验提示
被错误分级当作 error**。例如"请先选择一个项目""请填写接口密钥""第 2 页标题
不能为空""分镜结构尚未通过校验"。它们在正常操作（顺序不对、表单没填完）时
就会触发，与真实故障混在一起，让用户无法分辨哪些是 bug。

### 调整

| 类别 | 处理 |
| --- | --- |
| 引导/校验提示（请先/请填写/请至少/不能为空/缺少/未通过/超过限制） | 一律静默。它们是预期交互，就地呈现（表单高亮、按钮禁用、步骤内状态条）即可，不再进入全局通知容器。 |
| 真实失败/报错（失败/错误/异常/被拒绝/中断/超时/无法/未能/不可用/无效/HTTP 4xx–5xx，或 ❌/⛔/🚫 前缀） | 继续短暂弹出，60 秒去重、屏幕最多一条不变。这是故障排查信号：弹出即失败。 |

各通道核对结果：视频、PPTX、TTS、一键生成、数字人、勾画标注任务的状态轮询
均已使用静默请求，本轮复核无遗漏；通用 API 层对真实请求失败的自动报错保留
（这正是排查所需的信号）；删除确认等模态框与旧产物显式修复询问不属于通知，
维持原状。
