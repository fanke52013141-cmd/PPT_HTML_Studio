# Pi Agent 无人交互 API 实施方案

2026-10-20。原实施提案，研究编号 RES-20261020-PI-01。M0–M3已实施并进行工程/真实模型验证，见[前序handoff](handoff-pi-agent-m0-m3-2026-10-20.md)。M4生产/预授权保存、M5项目候选/显式选择已接线，最新事实见[M4–M5工程交付](handoff-pi-agent-m4-m5-2026-10-20.md)；默认切换和旧编排清理待真实门槛。下文保留原计划及示意接口，实际接口以能力矩阵和正式契约卡为准；新页复用produce，不新增第二个scene.generate接口。

## 产品目标与决定

将 AI 生成和 AI 修改统一成任务 API：一次提交完整输入，后台自主调用工具、检查和修复，返回固定结构结果。执行中不向人提问、不等待人工点击；不能完成就返回可机器处理的失败。人工编辑作为独立入口，可以在执行前设置保护，也可以在结果返回后接管。

采用完整 Pi Coding Agent 的 SDK 构建专用执行服务，复用其会话、工具循环、上下文和事件机制，不从 pi-agent-core 重新搭建 Agent。Python 应用保持业务入口，Node 执行进程承载 Pi。初期本机子进程通信，公开 API 由 Python 统一提供；不引入第二套项目数据库或第二个可运行应用副本。

“拿来即用”体现为安装依赖、配置模型、点击运行即可使用；业务工具、结果验证和项目权限仍须适配。固定输入输出不等于同一模型每次产生相同作品。

## 现状与迁移原则

- `html_candidate_agent.py` 当前采用 LangGraph；它是既有局部修复编排，不据此判定全部问题由框架造成。
- 外部任务包、delivery.zip、原预检、原 DOM 预览、人工保护、候选工作台和历史恢复已经存在；优先复用。
- 当前四类评测能准备和记录任务，但不负责运行外部模型。真实 Pi 自主成功率尚未知。
- 先建立统一执行接口，使 Pi 与旧执行器可按任务类型切换。每种任务验收后切换默认执行器；确认无引用后删除旧编排及不再使用的依赖。
- Pi 服务所有生成产物通过原业务服务验证和落盘。Agent 会话不作为项目状态或作业状态的权威来源。

## 服务与职责

| 层 | 职责 |
| --- | --- |
| 页面/外部调用方 | 提交任务、查询进度、获取结果、主动取消；人工编辑独立 |
| Python 业务 API | 身份、输入快照、权限、幂等、预算、作业持久化、验收、结果发布 |
| Pi 执行服务 | 无交互会话、模型决策、调用已授权工具、处理反馈、提交候选 |
| 原业务工具 | 规划、图像/TTS 等现有供应商适配、编译、截图、测量、动画绑定、保存 |
| 原编辑器 | 画布、中文属性、关联组、人工保护、版本恢复 |

初始建议文件边界（创建前复核项目实际结构）：`agent_runner/` 管理固定版本 SDK、会话和工具适配；`html_agent_jobs.py` 管理业务任务生命周期；`html_agent_routes.py` 为薄 Web 适配。共用模型进入 `agent_contract/models.py`，业务操作仍归原服务所有。不把 HTML 静态修改语义复制到 Node。

工具采用显式注册和任务级授权。候选工具族包括读取任务材料、读取实际截图、提出候选操作、调用原预检/预览、读取反馈、提交结果。名称和 Schema 在定义阶段锁定，不能把本方案示意名冒充现有 API。不默认启用任意 shell、全盘文件访问或用户目录自动发现的扩展。任务目录只是数据隔离；若开放任意代码执行，必须另有 OS/容器权限隔离。

## 固定输入

建议公开协议 `agent-job/1.0`；任务内容继续引用现有版本化合同。以下为新 API 示例，尚未实现：

```json
{
  "schema_version": "agent-job/1.0",
  "idempotency_key": "client-generated-unique-key",
  "task_type": "scene.repair",
  "project_id": "project-id",
  "baseline": {"revision": 12, "snapshot_id": "server-issued-id"},
  "input": {
    "task_bundle_id": "server-issued-task-id",
    "instruction": "把底栏字号改为26px，同时保持内容完整并修复容量问题"
  },
  "execution_profile": "html-visual-default",
  "limits": {"max_candidate_rounds": 2, "timeout_seconds": 600},
  "delivery_policy": "candidate"
}
```

服务端解析并封存：准确原文、风格/模板、场景和对象身份、素材与哈希、当前截图、音频与绑定、scope、人工保护、目标条件、允许操作、必需能力、合同/工具/模型版本。客户端不能通过 instruction 覆盖这些约束。

输入不完整时明确列出缺失字段，返回 `invalid_input`；原任务过期返回 `stale_input`；不会在会话中等待用户补充。模型与工具配置由执行配置引用，不把 API 密钥放在任务包或日志里。输入中的 URL/路径必须经业务解析，不直接转为任意文件读取或网络访问。

## 固定输出与 API

建议接口：

- `POST /api/agent/jobs`：校验并创建，202 返回 job_id 和查询地址。
- `GET /api/agent/jobs/{id}`：状态和稳定进度。
- `GET /api/agent/jobs/{id}/result`：终态结果。
- `GET /api/agent/jobs/{id}/events`：可选 SSE；断线不取消作业。
- `POST /api/agent/jobs/{id}/cancel`：请求协作取消。

作业状态为 queued/running/succeeded/failed/cancelled/interrupted；重试阶段由 progress 描述。失败代码另设 invalid_input、unsupported_capability、constraints_unsatisfied、stale_input、budget_exceeded、provider_error、timeout、verification_failed。终态由服务端签发，不采信模型自报成功。

```json
{
  "schema_version": "agent-job/1.0",
  "job_id": "job-id",
  "status": "succeeded",
  "task_type": "scene.repair",
  "baseline_revision": 12,
  "delivery": {
    "kind": "candidate",
    "artifact_id": "delivery-artifact-id",
    "result_schema_version": "0.2.0",
    "saved_revision": null
  },
  "verification": {
    "structural": "passed",
    "dom": "passed",
    "model_visual_review": "self_checked",
    "human_approval": "not_requested"
  },
  "usage": {"candidate_rounds": 1, "cost": null},
  "error": null
}
```

输出由宿主依据已校验候选、工具回执和作业记录序列化。Pi 的 JSON 事件流不是此业务 JSON；模型文字也不直接作为 API 返回体。错误使用同一外壳，delivery 可为 null，error 带 code/message/retryable/details。失败的中间候选只能作为诊断附件，不能放入可采用交付字段。

`succeeded` 表示本任务指定自动验收及交付完成；不冒充人工批准。要求人工批准才能完成的旧任务不能进入无人模式，提交前返回不兼容要求。若未来要自动发布正式成片，须另行定义自动验收策略和现有批准状态迁移，不能伪造原批准字段。

## 自动执行闭环

1. 校验输入、能力、版本、预算和授权；固定只读基线。
2. 创建隔离任务工作目录和无交互 Pi 会话，注入版本化任务合同和白名单工具。
3. Agent 读取材料、实际图像，生成候选。修改通过原操作 Schema；全新场景通过注册生成接口。
4. 运行原静态检查、实际浏览器预览、截图和任务所需动画采样。要求视觉判断时把真实图像交给视觉模型，记录证据来源与时间。
5. 宿主检查目标条件和保护字段。未过则把实际反馈交还同一任务；首轮加一次反馈修复，默认共两轮候选。
6. 全部必要条件通过后封装交付；不可完成则返回稳定失败，附可解释诊断。
7. 依据交付策略保存候选或另存新修订，记录结果和产物后进入终态。

候选轮次、模型请求数、工具调用数、费用和墙钟时间分别限额；两轮候选不等于只有两次模型调用。工具超时和供应商重试同样计入预算。缺必需视觉/音频能力时停止，不无限自修复或自动换付费供应商。

## 无人执行与人工编辑

第一版 `candidate`：执行全程无人参与，返回已验证候选，用户后续可人工编辑。这不要求在任务中确认。

第二版 `save_revision`：用户在提交时预先选择自动保存，系统在验收通过、基线仍新鲜、保护条件成立时另存新版本。保存为 AI 来源，保留历史；不能调用人工 work/propose/confirm 来伪造人工操作。与当前显式保存规则的差异须在实施该阶段时正式修订契约和权限。

运行中人工编辑不被锁死；若作者/音频/相关规则发生变化，本任务返回 stale_input 并保留诊断，不静默覆盖，也不在原任务中自动扩大基线。

人工接手后仍可拖拽、改属性、按关联组采用、撤销和恢复历史。人工修复成功与 Agent 自主成功独立计分。

## 任务覆盖顺序

| 阶段 | 任务 | 复用及边界 |
| --- | --- | --- |
| 第一批 | 静态局部修改、动画绑定修改 | 原 repair、编辑、预览和保护 |
| 第二批 | HTML 新页生成、按参考图还原 | 原规划、设计、素材、场景编译；需新增 generation 类型合同，不能套用 repair 的20操作范围 |
| 第三批 | 文章生成、分镜规划、批量页面优化 | 原文章和 storyboard 服务；子页状态、失败隔离、批量预算 |
| 第四批 | 图像、配音、音画绑定等流程的自动调用 | 复用现有供应商、持久作业和原确认语义；新增无人模式需显式契约 |

图像/TTS 本身继续由现有模型服务生产，Pi 决定何时及带哪些合法参数调用。渲染器、画布、音频合成、文件导入导出等确定性功能继续由程序执行。

## 可靠性与成本

- 使用现有 local_jobs 的生命周期约定；若字段不足，增加下一编号 migration，不修改已应用迁移。Pi JSONL 只作执行证据。
- 同一身份、同一幂等键和相同输入返回同一任务；键相同而输入不同返回冲突。保存使用基线 revision/hash 和原原子事务。
- 付费工具保存调用意图和供应商 job_id。网络结果不明时先查单；不可查明就中断返回，不盲目重复生图/TTS。
- 重启后恢复作业事实；会话可恢复不意味着外部副作用可以安全重放。未知调用结果保留 interrupted。
- 用户取消后停止新调用；已提交的远端调用是否取消取决于供应商，结果如实记录。
- 保存并发控制、预算、工具权限和通过判定由服务端执行，不能仅写入提示词。
- 默认固定依赖版本与 lockfile、固定工具/提示词版本；升级在隔离评测通过后启用。会话与媒体按项目隔离并纳入保留/清理策略。

| M3 页面集成 | “AI修改”直接启动任务、进度/取消、返回结果和人工接管 | 无需人工搬运ZIP；原导入导出兼容；候选画布和版本恢复回归通过 |

建议先完成 M0–M3，形成用户可直接使用的无人修复功能，再扩展 M4–M5。M0定义后按实际接口数量拆工期，避免在未做真实模型联调前承诺准确天数。

## 对照评测与上线条件

固定模型、输入、工具能力、预算，比较旧执行器与 Pi，不能用更强模型造成的提升证明框架提升。保留现有四类：布局、动画、人工保护、缺能力停止；增加新页生成、基线并发变化、供应商超时/未知结果。

首轮验证每类真实执行一次，暴露接口问题；发布前布局与动画各至少10次，保护和缺能力各至少5次。样本小，报告原始分子/分母，不宣称普遍可靠。建议初始产品目标：可解修改案例两轮内成功率≥90%，保护误写和缺能力误报成功为0，所有任务有终态且无人工中途参与。未达标时保留实验入口并定位模型、工具、规范或执行器原因。

同时记录首轮成功率、二轮恢复率、人工介入、目标偏离、耗时、模型/工具请求数和成本；未知费用为null。自动视觉审查不等于人类审美验收，真实作品盲审结果另记。修改任务与新页生成分别统计。
