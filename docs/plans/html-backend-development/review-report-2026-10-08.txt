三、发现的问题（按优先级）
------------------------------------------------------------------------
P1【高】入口 README 执行进度段过时，且与账本直接矛盾
  现象：README.md 第 22 行写"C01—C04、D01/D03、E02/E03、F01—F03 本轮
  未实施（记 not_run）"，但这些任务已于 02:20–03:33 全部实现并提交
  （git log 可证），task-ledger.json 已记 passed/partial。README 写于
  01:55 后未再更新。
  影响：agent-handoff.md 要求执行 Agent 首先读 README，接手者会据此
  误判进度，可能重做已完成任务或跳过未完成任务。
  建议：更新该进度段至当前状态；或删除手工进度段，改为声明
  "进度以 task-ledger.json 与 acceptance-manifest.json 为唯一事实源"
  （手工维护的进度段已被证明必然滞后）。

P2【高】账本任务状态与方案自身放行规则冲突（状态语义抬高）
  现象：task-ledger.json 中 F03 记 "passed"，但其 note 自列 4 项放行
  剩余（用户 AC04 视觉结论、用户 AC20 真实课程导览、真实模型服务绑定、
  PowerPoint 打开核验），而 acceptance.md 明确"视觉有明确用户审阅结论"
  是放行条件。F03 应为 partial / pending_review。
  同类：A02 与 C04 的 acceptance 列表含 AC04（pending_review）却记
  passed；B03 的 acceptance 列表含 AC20（pending_review）却记 passed。
  影响：下一个 Agent 读到 "passed" 会把视觉门槛当成已关闭——正是方案
  明令禁止的"用测试数量替代验收证据"。
  建议：将状态改为按 AC 分列，例如
    "acceptance_states": { "AC02": "passed", "AC04": "pending_review" }
  或至少把含未过 AC 的任务统一降级为 partial，并在 README 约定 status
  字段仅表示工程实现状态。

P3【中】13 个任务的 "commit": "this-round" 是占位符
  现象：违反 agent-handoff.md 交付清单要求的"提交 hash"。
  实际提交均已存在，可直接回填：
    C01=2fb4fb5  C02=6190105  C03=b31043a  C04=2a5c925
    D01=aaef8d9+90f9c60  D03=e0a4e14  E02/E03=b11bedb
    F01=fa8aa6d  F02=f4fa3e7  F03=3259fce  （UI 收尾=09732e0）
  建议：回填真实短 hash，使证据可追溯。

P4【高】AGENTS.md 已过时，且未登记新模块所有权
  现象：工作区、本地 HEAD、origin/main 三处的 AGENTS.md 均仍写
  "The current application still runs the original image workflow;
  the HTML backend is planned, not implemented"，与实际状态（B01-B03、
  C01-C04、D01-D03、E01-E03、F01-F02 已实现并注册）不符；模块所有权
  清单未登记 html_visual_store / html_visual_routes /
  html_visual_review_service / html_visual_review_routes /
  html_render_runner / html_task_store / html_action_editing /
  html_audio_binder / html_annotation_targets / html_pptx_snapshot /
  html_design_brief / html_asset_service / html_storyboard_planning /
  static/html_review_panel.js；checks/test_frontend_quality.js 也未给
  新面板加所有权守卫（AGENTS.md 对新抽取模块的既有惯例）。
  影响：任何新 Agent 读 AGENTS.md 会认为 HTML 后端不存在，可能绕开
  既有模块重新造轮子或错误套用 image 门槛。
  建议：更新 AGENTS.md 的 HTML 后端状态描述；按既有格式补登记
  html_* 模块所有权；为 html_review_panel.js 补前端所有权守卫。

P5【中】工作区脏状态威胁"按文件范围审查/提交"
  现象：git status 显示 137 个"改动"文件，其中约 113 个为 CRLF 换行
  噪音（--ignore-cr-at-eol 后无差异）；其余 24 个文件（约 +1046/−550
  行）为复制时遗留的真实未提交改动（scripts/build_portable_package.ps1、
  启动.bat/停止.bat、digital_human_routes.py、README.md 等，记录于
  docs/baseline/source-snapshot.json）。
  影响：F03 要求"只审查并提交本轮明确范围文件"，此状态下一次
  git add -A 即会把遗留改动混入提交。
  建议：新增 .gitattributes 固定换行策略并一次性 renormalize 消除
  噪音；遗留改动单独提交到 baseline 记录分支，或明确列入永不提交
  清单。

P6【低】acceptance-manifest.json 两处小过时
  a) "published_to" 仍写 "origin/main 23af1f1"；main 已前进至 5d522b4
     （23af1f1 为其祖先，发布链成立，仅引用过时）。
  b) "remaining_for_full_signoff" 第 5 项"workspace UI panels"已在
     03:31 的 09732e0 交付（static/html_review_panel.js 已存在并接入
     static/index.html:1842），03:33 最后更新 manifest 时未划掉。
  建议：同步这两条，保持 manifest 与仓库状态一致。

五、前瞻性建议（方案/流程优化）
------------------------------------------------------------------------
1. 账本 schema 增加按 AC 分列的状态层（见 P2），消除"任务 passed 但
   某 AC 未过"的歧义；建议在 acceptance.md 中固化该字段格式。
2. README 不再手工维护执行进度段，统一指向 task-ledger.json 与
   acceptance-manifest.json（见 P1），或约定每轮交付强制同步 README。
3. 性能风险应前置验证：E01 浏览器逐帧截图方案目前仅有单页 12s 冒烟
   （1600×900 H.264+AAC）；整门课（数十页 × 长音频）的批量渲染吞吐
   未测。建议在 AC20 之前先跑一次多页课程渲染计时；若吞吐不可接受，
   需要在真实课程验收前调整导出策略，而不是验收过程中发现。
4. 真实服务证据补齐后，记得按方案闭环更新 acceptance-manifest 的
   blocked_on_service_evidence 与 C02/C03 的 note，避免账本与事实
   再次脱节。
