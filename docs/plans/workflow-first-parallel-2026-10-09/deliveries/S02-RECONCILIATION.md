# S02 结果对账与作者提交恢复交接

2026-10-12。契约0.9.24、恢复定义0.2.0、操作Skill1.2.2。延续原任务和 LocalJob，不新增数据库或生产服务。

## 本轮行为

1. 供应商响应已写文件但数据库未登记：请求回执绑定 job/snapshot/attempt/request 与结果散列，对账可补回 returned，随后由原校验链续跑，不重复生图。
2. ToAPIs 已创建但轮询失败：创建响应拿到 task_id 后、第一次 GET 前立即持久化；新回执也覆盖此登记失败窗口。恢复校验原图片连接配置，只查询旧 task_id，并跳过参考上传和生图 POST。
3. 作者已保存但成功状态未写回：写文件前 prepared 记录预期散列，完成后 sealed 封存实际散列；服务启动与同输入提交都先核对完整作者文件。匹配则恢复原任务成功，不新建生产任务或改写作者文件。
4. 下游失效的数据库修改与任务终态同一次提交；保留原音频确认和人工视觉批准门禁。任务读接口添加 reconciliation，Agent 的 task dict 与 Web 沿用同一结构。
5. 坏回执、错误供应商请求身份、缺文件、新 revision、旧 attempt、cancelled 和换连接不会虚报恢复。未拿到 task_id 的同步超时继续阻断补发。

## 实现归属

- html_production_recovery.py：回执核验、供应商对账、作者提交对账。
- html_production_stages.py：请求意图、原始返回与 task_id 的回执/CAS 登记。
- html_workflow_jobs.py：启动/再提交对账与原任务恢复。
- html_production_service.py：锁内写前清单、保持作者保存语义与写后封存。
- html_image_provider.py / ai_provider_service.py：HTML 原任务继续查询；共享 ToAPIs 可选任务 ID 回调、resume 不再上传参考。默认调用行为保持。

## 验证与限制

最终联合回归118项通过：阶段恢复、对账故障注入、任务 store、快照、E生产、实际工作流、图片参数、共享供应商与重试策略。Skill结构校验、Agent契约生成检查和 git diff --check 通过。没有使用真实用户数据库或运行目录，没有启动第二服务；pytest 使用既有临时隔离配置。

故障实验覆盖返回落盘但登记失败、远端成功/仍排队/查不到/身份错误、跨恢复查询预算、作者已保存但终态登记失败、prepared 完整但缺最后 sealed、作者文件删除/改动/新版本及取消保护。实际生产案例使用原共享浏览器做静态检查，供应商网络为模拟，未调用付费模型。

ToAPIs 传输模拟确认仅一次首次生图 POST，task_id 先于首次轮询入库；故障后只 GET 原任务。resume 即便携带旧 reference_paths 也不上传。普通无 ID 接口不能可靠查单；不猜测接口、不补发、不保证远端恰好一次。每请求最多三次查询会话，ToAPIs 每次30秒轮询窗口，不等于三次 HTTP 请求。

完整作者文件和回执不一致时要求核实；不自动补写部分文件或覆盖后续人工编辑。真实远端查单、无 ID 请求的人工处置界面和底层 HTTP 累计预算仍需另验/另开发。
