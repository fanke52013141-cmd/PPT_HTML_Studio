## 1. 判断与建设顺序

报告最有用的部分，是把内容、布局、素材、时间与渲染拆开。我们可以借鉴这些机制，
但应继续以自己的场景契约为中心：公共组件和布局负责组织内容，风格包提供视觉表达，
场景实例保存讲稿与动作绑定，渲染器生成 HTML 和视频。

首先定义可复用的数据和组件接口，再用一种风格做样板。不要先全面迁移到 HyperFrames、
Slidev 或 PPTist；报告的工程工具不能替代我们的风格、组合、美感与兼容规则。

优先级定义：P0 是首个样板的基础；P1 是样板闭环及选型验证；P2 是扩展能力。

## 2. BOR-01：让模型填写语义场景，系统完成排版

PPTist 的启发是结构化页面数据与渲染分离。其官方资料提供了 AI 页面数据结构说明，
但这不能直接证明项目具有完整 JSON Schema 运行校验，也不能证明有效数据必然美观。
参考：[PPTist AI 数据说明](https://github.com/pipipi-pikachu/PPTist/blob/master/doc/AI_PPT_SCHEMA.md)。

我们的结构化输入应该表达“是什么、放在哪类区域、何时讲到”，而不是要求模型计算每个像素：

- 页面：教学目标、布局引用、风格引用、组件实例、讲稿、动作绑定和资源引用。
- 组件：公共类型、稳定身份、内容属性、可选公开目标；几何结果由布局生成。
- 布局：插槽、容量、可接受组件、约束和溢出策略。
- 素材请求：用途、画风引用、构图、比例、是否透明、是否需要独立控制。
- 动作：目标身份、讲稿锚点、动作类型与允许参数；实际时间作为派生数据。

校验至少分四层：字段格式与类型；引用/支持集；排版容量与几何；视觉审阅。
例如，合法的五百字正文仍可能装不进一个说明卡。应该报告具体问题并缩写、拆页或换布局，
而不是默默缩到不可读的字号。

正文中的字段说明是待定义接口范围，尚不是正式 Schema。第一步应填写定义卡并确定
最小字段、默认值、必填项、限制、错误码、版本和迁移方式，再实现 Schema。

## 3. BOR-02：插槽布局是公共能力，风格提供受约束的呈现

Slidev 支持自定义布局和命名插槽，可借鉴其内容分发方式。
参考：[Slidev 自定义布局](https://sli.dev/guide/write-layout)。

首个样板沿用既有路线，先做左右布局；再验证标题与主视觉、步骤列表。每个布局都有明确的插槽定义，
例如标题、解释、主视觉、页脚，以及可选数字人保留区。每个插槽定义组件支持、数量、
文本容量、最小尺寸和相互关系，而不是仅给一个 CSS 类名。

| 内容 | 公共定义 | 随风格变化 | 页面填写 | 系统计算 |
| --- | --- | --- | --- | --- |
| 讲解卡 | 标题、解释、图标和公开目标 | 字体、边框、底色、装饰变体 | 具体文字、图标语义 | 分行、尺寸、位置 |
| 双栏布局 | 两栏语义与容量关系 | 被允许的比例、留白、视觉重心 | 两栏中的组件和素材 | 最终栏宽与坐标 |
| 插图 | 资源身份、比例、控制粒度 | 画风、材质、线条、色板 | 主题与构图要求 | 缩放、裁切与资源就绪 |
| 动作 | reveal/highlight 等语义与状态 | 被允许的时长、缓动和强调表达 | 目标与讲稿锚点 | 指定时刻的状态 |

公共组件定义职责与接口；风格可以选择公共呈现变体和组合配方，不应复制一套业务组件。
有新表现需求时，先看能否增加可复用变体，而不是增加“某风格专用组件”。

布局种类可逐步覆盖常见教学结构，但“十种布局足以保证所有内容不崩坏”不能作为承诺。
长文、中文字体、竖屏、表格和数字人占位都可能要求不同的容量与降级策略。

## 4. BOR-03：渐进显示保留占位，目标在生成时就已明确

Slidev 默认用透明度隐藏点击目标，提供了保留文档流位置的参考；它的点击步序不是
语音时间轴，默认 transition 也不能直接当作逐帧导出动画。
参考：[Slidev 动画说明](https://sli.dev/guide/animations)。

我们的普通 reveal 应保持几何占位，只改变呈现状态。隐藏目标还需要明确交互、焦点与
无障碍策略；只设置 pointer-events 不能解决全部交互问题。需要移动其余内容的动作，
必须声明为重排并单独验收。

HTML 的准确定位来自可测量的目标树及坐标变换，不是原始 DOM 像素直接等于输出坐标。
缩放、旋转、容器裁切和字体变化仍需处理。文字描线/圈画绑定文本范围或公开目标，
使用排版结果求几何；复杂位图内部区域没有因此自动获得结构化目标。

因此，自动标注可以从“识别整页图片中的对象”改为“模型选择现成的目标身份并关联讲稿”。
人工编辑可以点选目标；自定义局部区域仍可用勾画工具。不必删除原图片后端的 OCR/Mask。

## 5. BOR-04：任何时刻都能直接求出画面

Remotion 的帧驱动方式与 HyperFrames 的 seek/捕获管线，给出了两种可参考的实现。
参考：[Remotion 基础](https://www.remotion.dev/docs/the-fundamentals)、
[HyperFrames 引擎](https://hyperframes.heygen.com/packages/engine)。

需要借鉴的是 `state = evaluate(sceneRevision, time)`：从第零秒播放到第三秒，
直接跳到第三秒，或从第五秒倒退到第三秒，都应得到同一修订的第三秒状态。
它是项目运行契约的具体落实方向，不要求用户认识底层渲染框架。

报告的 `videoTime == start` 触发方案应修正。帧采样可能永远碰不到精确时间戳，
倒退也不会撤销已经触发的动作。应该根据区间与进度求值，统一定义边界、缓动、冲突优先级
和结束态；禁止依赖上一帧执行过什么来获得正确状态。

适配器候选接口包括载入固定修订、等待就绪、按整数帧 seek、捕获帧和返回诊断。
这些是待正式定义的接口职责，不能直接当作已实现 API。
浏览器交互预览与视频导出可以有不同运行方式，但必须共享求值逻辑并核对关键帧。

## 6. BOR-05/BOR-10：资源就绪与可复现环境

资源加载完成、图片解码、字体可用、媒体就绪、布局稳定都应进入 capture 前的检查。
失败时明确阻止导出或使用已声明的降级，不应依赖固定等待几秒。
Remotion 的等待机制可作为实现参考，而不是将其概括为只靠猜测等待。
参考：[Remotion delayRender](https://www.remotion.dev/docs/delay-render)。

每次任务需要固定：场景/规则/风格/组件版本、素材与字体哈希、画布、帧率、浏览器、
渲染器、编码参数及环境信息。随机效果必须固定种子；输出阶段避免依赖不可控远程资源。

内联 base64、随作品打包的本地资源、受控资源服务都是实现选项；“可复现且就绪”才是要求。
大素材全量内联会影响体积与内存，应测量后决定。并行分片须保持相同输入修订、环境、
帧区间及音频拼接策略。十倍速是待测性能指标，不能先写成承诺。

HyperFrames 的低层帧控制值得验证，但渲染环境、字体、资源、非确定性代码仍需受控。
相同 HTML 在任意机器必然像素一致的结论不成立。
参考：[HyperFrames 确定性约束](https://github.com/heygen-com/hyperframes/blob/main/skills/hyperframes-core/references/determinism-rules.md)。

## 7. BOR-06：音频决定时间，讲稿锚点连接视觉目标

Manim Voiceover 的词语书签机制适合借鉴为讲稿锚点；WhisperX 提供语音对齐能力。
参考：[Voiceover 书签](https://voiceover.manim.community/en/stable/quickstart.html)、
[WhisperX 官方项目与限制](https://github.com/m-bain/whisperX)。

应该分开三个问题：视觉对象身份由组件/目标树提供；哪句话对应什么对象由讲稿绑定提供；
这句话何时说到由 TTS 时间戳或对齐结果提供。强制对齐只解决第三个问题，不能切开粘连位图。

建议优先使用可信的 TTS 时间戳，缺少时调用已有对齐能力；WhisperX 作为候选，
不因报告推荐就重建现有服务。保留讲稿原文、朗读规范化文本及两者映射，处理数字、
英文缩写、标点、重复句、停顿、漏读和用户替换音频。

对齐结果应记录来源、模型/服务版本、质量状态与人工修订；无时间或低质量时保留诊断，
允许句级降级或人工校准。不能把三位小数的时间戳格式当成一毫秒准确率。

音频真实时长加上明确的开场、停顿、尾部余量决定页面持续时间。帧数转换统一规定舍入，
最好从全局边界/整数采样计算，避免逐句取整累积漂移。换音频应失效对齐、动作时间和
数字人口型产物，保留语义目标及可复用素材。

## 8. BOR-07：人工调整写回结构化数据

有价值的是编辑器写回机制，而不是报告提到的插件名称。对 `slidev-addon-studio`
及其宣称的完整回写能力，本次没有取得足够可靠的一手证据，不作为依赖依据。

拖拽应写成受约束的实例覆盖，例如偏移、尺寸、裁切或插槽选择；不要只修改 DOM 或
把计算坐标固化成语义内容。每个覆盖记录作者来源、作用对象和依赖的布局版本。
重新排版或切换风格时校验覆盖是否仍有效；不兼容项保留并提示修复，避免静默覆盖。
人工改讲稿时间与人工改位置应分别管理，生成器不得无条件重写。

## 9. BOR-08/BOR-09：直接复用现有数字人方案

2026-10-07 用户明确当前方向：数字人直接使用现有方案，不需要从报告借鉴或重新选型。
这取代本档案初稿中“后续更换模型”和“保留 Rhubarb 候选”的建设建议；旧研究的来源核对
继续保留在 source-checks.md，避免丢失分析依据，但不形成当前开发任务。

现有数字人生成、口型处理、任务和产物接口直接复用。HTML 路线只需接入其视频产物，
验证三件事：人物位置/大小/裁切与内容避让；旁白与人物轨道的时间同步；最终视频合成。
背景处理沿用现有方案及实际产物格式，不新增模型或抠像技术路线。
人物音轨不重复叠加，失败、等待和禁用状态沿用现有服务并验证新入口。

因此 BOR-08 定位为现有能力复用，EXP-07 仅验证接入；BOR-09 不安排实施与实验。

## 10. 报告没有解决，但本项目必须补齐的部分

| 缺口 | 为什么仍需要 | 后续定义位置 |
| --- | --- | --- |
| 美感系统 | 时间正确和字段合法不会自动产生好看页面 | 风格包定义卡、组合配方、参考页与视觉审阅 |
| 可独立生成的素材 | 整张漂亮背景无法支持内部元素逐项出现 | 素材用途、独立控制粒度、透明背景/安全留白与文字避让 |
| 容量和失败策略 | 长文本、中文、窄屏与复杂图表可能溢出 | 布局定义卡、容量样例及可诊断降级 |
| 作品身份和人工修改 | 重新生成不能破坏绑定与已修订内容 | HPS-006、010、011、016 |
| PPTX 输出 | 浏览器页面不会自动变成原生可编辑 PowerPoint | HPS-012 的支持集、栅格降级、字体与动画差异验证 |
| 安全边界 | 模型或素材中的任意脚本不能直接获得应用权限 | 受控组件、富文本清洗、资源访问边界与渲染隔离定义 |
| 成本、部署和许可 | GPU 模型/框架能演示不等于适合 Windows 本地产品 | 候选版本、资源预算、代码/模型/字体/素材许可确认 |

关于美感，保留我们已有路线：公共原子和讲解组件 → 布局 → 风格配方 → 实例。
AI 生图主要提供独立插画、照片、纹理和必要背景；标题、课程文字、数据、箭头等需要
编辑与准确控制的对象优先使用 HTML/SVG。每种风格有一组人工审阅通过的参考页，
并验证换内容后仍成立。报告提供了工程机制，不能替代这一步。

## 11. 从文档到首个样板

1. 填写核心定义卡：场景、Text/Image/讲解列表组件、布局插槽、公开目标、讲稿锚点、
   reveal/highlight 动作、资源就绪与渲染适配器。
2. 选择一种风格，先制作左右布局参考页，再扩展到三种布局；换长短内容与素材检查容量。
3. 加入讲稿与真实音频；按锚点显示内容，验证跳转、倒退、重复定位和手动校准。
4. 用同一场景比较候选渲染方案，形成有环境和结果的选型记录。
5. 验证视频及 PPTX 支持/降级，再接入原项目公共应用服务；数字人直接复用现有方案，验证 HTML 接入。

这样分析形成可追踪的输入：借鉴编号 → 定义卡/HPS 规则 → 实验 → 决策 → 实现验收。
不需要为了保存调研先动应用业务代码，也不需要把所有候选同时接入。
